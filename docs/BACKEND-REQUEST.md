# Запрос в бэкенд: что нужно фронтенду health-ai-frontend

Кому: команда бэкенда Health AI  
От: фронтенд (сайт, репозиторий `avavion/health-ai-frontend`)  
Дата: 6 сентября 2026  
Приоритет: 1 и 2 блокируют публикацию сайта и карточки в App Store.

> **Статус: выполнено 6 сентября 2026.** Реализовано в `health-ai-backend`,
> контракт описан в §16 `docs/BACKEND_API.md`. Расхождения с запросом — три,
> все ниже по тексту: адрес обращения не хранится, ошибки приходят в конверте
> §2, вебхука перевалидации нет. Документ оставлен как есть — по нему видно,
> о чём договаривались.

Сайт собран и работает, кроме двух мест: отправка формы поддержки и третий
правовой документ. Ниже ровно то, что нужно реализовать, с контрактами, на
которые фронтенд уже рассчитан. Ничего менять на фронте после реализации не
потребуется — только переменные окружения.

---

## 1. Приём обращений в поддержку — новый роут

**Зачем.** Apple требует рабочий канал связи на странице поддержки приложения.
Сейчас форма валидирует ввод и получает 501 от заглушки, показывая пользователю
адрес почты. Это временное решение, для релиза нужен настоящий приём.

```
POST {API_BASE_URL}/support/requests
Content-Type: application/json
```

Без авторизации: обращение может прислать человек, потерявший доступ к аккаунту.

### Тело запроса

| Поле | Тип | Обязательное | Описание |
| --- | --- | --- | --- |
| `email` | string | да | Почта для ответа |
| `topic` | enum | да | `app-question`, `bug`, `account-recovery`, `account-deletion`, `data-question`, `other` |
| `message` | string | да | Не короче 10 символов, не длиннее 5000 |
| `consent` | boolean | да | Всегда `true`, без согласия форма не отправляется |
| `locale` | string | да | `ru` или `en` — язык, на котором ждут ответ |
| `name` | string | нет | Имя, если указано |
| `userAgent` | string | нет | Заполняет клиент, помогает разбирать баги |
| `appVersion` | string | нет | Если обращение пришло из приложения |

```json
{
  "email": "anna@example.ru",
  "topic": "bug",
  "message": "Приложение падает при сохранении обеда.",
  "consent": true,
  "locale": "ru",
  "name": "Анна",
  "userAgent": "Mozilla/5.0 (iPhone; CPU iPhone OS 18_5 like Mac OS X)"
}
```

### Ответы

| Код | Тело | Когда |
| --- | --- | --- |
| 202 | `{ "ticket": "HA-482913" }` | Обращение принято |
| 400 | конверт §2 с `details` по полям | Не прошло серверную валидацию |
| 429 | конверт §2 с `retry_after` | Слишком частые обращения |
| 5xx | конверт §2 | Фронтенд покажет «напишите письмом» |

> **Реализовано иначе.** Ошибки приходят в общем конверте §2 — том же, что у
> всех остальных маршрутов, — а не в отдельном формате. Своя форма ошибок на
> одном маршруте означала бы вторую карту кодов для клиентов; сайт всё равно
> раскладывает `details` по полям формы сам.

`ticket` показывается пользователю как номер обращения. Формат свободный, удобно
`HA-` плюс шесть цифр — тогда номера сайта и приложения выглядят одинаково.

### Что делает сервер

1. Повторно валидирует поля: на клиентскую проверку полагаться нельзя.
2. Ограничивает частоту: не более 5 обращений с одного email и 20 с одного IP в час.
3. Пишет обращение в таблицу `support_requests` с датой и локалью.
4. Отправляет письмо на `support@healthai.app` с `Reply-To` из поля `email`.
5. Отправляет пользователю подтверждение с номером обращения.
6. Удаляет обращение через 12 дней после закрытия — этот срок уже заявлен в политике.

> **Реализовано иначе: IP-адрес не хранится.** По той же причине, по которой
> его нет в `sessions` (§4.4, §12): адрес нужен ровно на время запроса, чтобы
> ограничить частоту, и хранить его — значит держать след перемещений там, где
> для работы поддержки хватает почты и текста. Счётчики частоты живут в памяти
> процесса, как остальные лимиты §11.

### Проверка

```bash
curl -i -X POST "$API_BASE_URL/support/requests" \
  -H 'Content-Type: application/json' \
  -d '{"email":"anna@example.ru","topic":"bug","message":"Падает при сохранении обеда.","consent":true,"locale":"ru"}'
# ожидаем 202 и {"ticket":"HA-..."}
```

## 2. Правовой документ `data-collected` — новый slug

**Зачем.** В приложении экран «Какие данные мы собираем» свёрстан нативно, но
Apple ссылается на веб-страницу из карточки приложения. Страница на сайте уже
есть и пока показывает заглушку.

Контракт тот же, что у существующих документов, менять ничего не нужно:

```
GET {API_BASE_URL}/legal/data-collected
Accept-Language: ru | en
```

```json
{
  "slug": "data-collected",
  "version": "2026-08-12",
  "title": "Какие данные мы собираем",
  "body_markdown": "## Перечень\n\n| Почта | Вход и восстановление доступа |\n..."
}
```

Текст обязан совпадать с `PrivacyInfo.xcprivacy` и анкетой App Store Connect —
редакцию согласуем перед публикацией.

Поддерживаемая разметка `body_markdown` (парсер повторяет iOS, набор закрыт):
`## Заголовок`, `### Подзаголовок`, абзацы, `1. Пункт`, `- Пункт`, `> Врезка`,
`| Метка | Значение |`, `---`, внутри строк `**жирный**` и `*курсив*`.
Всё остальное выводится обычным абзацем, но лучше в тексте не использовать.

## 3. Локализация правовых документов

Сайт двуязычный и отправляет `Accept-Language: ru` либо `en`. Сейчас неясно,
учитывает ли его роут `/legal/{slug}`.

- Если английские редакции есть — отдавать их по заголовку.
- Если нет — отдавать русскую и вернуть `"locale": "ru"` в теле, чтобы сайт мог
  показать пометку «доступно только на русском». Поле опциональное, фронтенд его
  примет, но не требует.

## 4. Технические условия

| Пункт | Что нужно |
| --- | --- |
| CORS | Разрешить `Origin` боевого домена сайта и `http://localhost:3000` для разработки на роутах `/legal/*`. Форма ходит через серверный route handler Next, для неё CORS не нужен. |
| Кеш | На `/legal/*` желателен `ETag` или `Cache-Control: public, max-age=300`: сайт держит ISR на час, но перепроверяет. |
| Вебхук | **Отложено.** Документ обновляется на сайте в течение часа, и этого достаточно: редакция меняется несколько раз в год. Когда понадобится быстрее — это настройка эксплуатации, а не изменение API. |
| Почта | Подтвердить, что ящик `support@healthai.app` существует и для домена настроены SPF и DKIM, иначе подтверждения будут уходить в спам. |
| Стенд | Адрес staging-API, чтобы прогонять сайт не против прода. |

## Критерии готовности

- [x] `POST /support/requests` отвечает 202 с номером обращения, письмо приходит на `SUPPORT_EMAIL` с корректным `Reply-To`.
- [x] Ограничение частоты возвращает 429, а не 500.
- [x] `GET /legal/data-collected` отдаёт документ в том же формате, что `privacy` и `terms`.
- [x] `Accept-Language` на `/legal/*` учитывается; в теле появилось поле `locale`.
- [x] CORS для домена сайта настроен (`CORS_ORIGINS`), предполётный запрос отвечает 204.
- [ ] Адрес staging-API — стенда пока нет, сайт проверяется против API разработки.

## Что сделал фронтенд

Заглушка 501 убрана, форма поддержки ходит в API через свой route handler.
Страница `data-collected` показывает документ с бэкенда. Переменные
`SUPPORT_TRANSPORT` и `SUPPORT_BACKEND_PATH` больше не нужны и удалены:
транспорт теперь один.

Вопросы: фронтенд, репозиторий `avavion/health-ai-frontend`, файлы
`docs/BACKEND-SUPPORT.md` и `docs/LEGAL-API.md` — там те же контракты подробнее.
