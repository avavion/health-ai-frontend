# Эксплуатация сайта

Выкатка, откат и то, что нужно завести на сервере один раз.

> **Адрес:** https://healthai.avavion.ru
> **Сервер:** тот же, что у API — VPS senko.digital (Германия), docker compose
> **Реестр образов:** ghcr.io/avavion/health-ai-frontend
> **Пайплайн:** [.github/workflows](../.github/workflows)

---

## 1 · Как устроено

Один контейнер, порт на петле, хостовый Caddy впереди.

```
        :443            /etc/caddy/Caddyfile
интернет ──► caddy.service ──┬──► health-ai-web   127.0.0.1:3100
             (на хосте,      │
              общий с        └──► health-api-*    127.0.0.1:8081/8082
              другими)                    │
                                          ▼
                                      Postgres
```

**Blue/green здесь нет, в отличие от API.** Причина не в экономии: у сайта нет
ни базы, ни миграций, ни долгих запросов. Перезапуск занимает секунды, а
переключать между поколениями нечего — вся его работа в том, чтобы сходить в
API и собрать страницу. Цена простоя на выкатке — эти самые секунды, и платить
за их отсутствие вторым контейнером и переписыванием конфигурации Caddy не за
что.

Что это даёт и чего не даёт:

- **Откат — это выкатка прежнего образа.** `deploy.sh` возвращает предыдущий
  сам, если новый не ответил за минуту; вручную — тем же скриптом с нужным
  тегом.
- **Сессии переживают выкатку.** Они лежат в cookie у человека и в базе API,
  а не в памяти сайта: перезапуск никого не разлогинивает.
- **API — отдельная выкатка.** Сайт и бэкенд живут в разных репозиториях и
  катятся независимо; общий у них только контракт.

Файлы на сервере в `/opt/health-ai-web`:

| Файл | Откуда берётся | Что внутри |
|---|---|---|
| `docker-compose.yml`, `deploy.sh` | приезжают из репозитория при выкатке | конфигурация, версионируется вместе с кодом |
| `caddy-site.conf` | оттуда же, справочно | образец секции для хостового Caddy; заводится один раз руками |
| `.env` | создаётся руками один раз | домен и порт на петле |
| `site.env` | создаётся руками один раз | адрес API и идентификатор устройства сайта |
| `images.env` | пишет `deploy.sh` | какой образ поднят сейчас |

## 2 · Что завести на сервере один раз

1. **Каталог и файлы окружения.**

   ```bash
   sudo mkdir -p /opt/health-ai-web && sudo chown "$USER" /opt/health-ai-web
   # после первой выкатки, когда приедут примеры:
   cp /opt/health-ai-web/env.example      /opt/health-ai-web/.env
   cp /opt/health-ai-web/site.env.example /opt/health-ai-web/site.env
   ```

   В `site.env` обязателен `SITE_DEVICE_ID` — постоянный UUID:

   ```bash
   uuidgen | tr '[:upper:]' '[:lower:]'
   ```

   У стенда и прода он должен быть разным: иначе они делят счётчик лимитов на
   чтение правовых документов (§15.1).

2. **Секция в хостовом Caddy.** Содержимое `caddy-site.conf` добавляется в
   `/etc/caddy/Caddyfile` под root, один раз:

   ```bash
   sudo tee -a /etc/caddy/Caddyfile < /opt/health-ai-web/caddy-site.conf
   sudo caddy validate --config /etc/caddy/Caddyfile
   sudo systemctl reload caddy
   ```

   Caddy отвергает неверную конфигурацию и оставляет работать прежнюю, поэтому
   соседние сайты при ошибке не страдают.

3. **Домен в DNS** — A-запись на тот же адрес, что у `health-api`. Сертификат
   Caddy выпустит сам при первом обращении.

4. **CORS на стороне API.** Сайт ходит в API своим сервером, и для основной
   работы CORS не нужен. Он нужен там, где запрос делает сама страница, —
   добавьте домен в `CORS_ORIGINS` в `app.env` бэкенда (§16.3).

5. **Секреты репозитория** для выкатки: `SSH_KEY`, `SSH_KNOWN_HOSTS`,
   `SSH_HOST`, `SSH_USER`, при нестандартном порте — `SSH_PORT`. Переменные
   (не секреты) `SITE_URL` и `SUPPORT_EMAIL` уезжают в сборку образа.

## 3 · Выкатка

Тег `v*` в `main` — и дальше само:

```bash
git tag v1.0.0 && git push origin v1.0.0
```

Окружение `production` в настройках репозитория держит ручное подтверждение:
тег ставят и по ошибке, а выкатка по нему уезжала бы молча.

Вручную с сервера:

```bash
/opt/health-ai-web/deploy.sh --image ghcr.io/avavion/health-ai-frontend:sha-abc1234
```

Скрипт записывает образ в `images.env`, поднимает контейнер и ждёт ответа на
`127.0.0.1:3100/ru`. Проверяется страница, а не открытый порт: порт означает
лишь, что процесс стартовал, а нам нужно, чтобы он собирал страницы — то есть
чтобы у него был доступ к API. Не дождался — возвращает прежний образ.

## 4 · Откат

```bash
# какой образ крутится сейчас
cat /opt/health-ai-web/images.env

# вернуться на предыдущий
/opt/health-ai-web/deploy.sh --image ghcr.io/avavion/health-ai-frontend:sha-<прежний>
```

Теги образов — короткие sha коммитов, они неизменны: по тегу всегда видно,
какой именно код поднят.

## 5 · Если сайт лёг

Порядок разбора — от дешёвого к дорогому:

```bash
docker logs --tail 100 health-ai-web          # что говорит сам сайт
curl -sS -o /dev/null -w '%{http_code}\n' http://127.0.0.1:3100/ru
curl -sS https://health-api.avavion.ru/health # жив ли API
sudo journalctl -u caddy -n 50                # дошёл ли запрос до сайта
```

Частые причины, в порядке убывания вероятности:

| Симптом | Причина | Что делать |
|---|---|---|
| Страницы дневника отдают ошибку, лендинг работает | API недоступен или сменил адрес | проверить `API_BASE_URL` в `site.env` и здоровье API |
| Правовые страницы показывают «документ временно недоступен» | API отвечает 4xx на `/legal/*` | проверить `SITE_DEVICE_ID` и лимит §15.1 |
| Всех разлогинило | отозвана цепочка сессий на API | смотреть лог API: повторное предъявление refresh-токена (§4.2) |
| 502 от Caddy | контейнер не поднялся | `docker logs health-ai-web`, затем откат |

## 6 · Стенд

Отдельного стенда у сайта нет: он поднимается локально против API разработки
(`make up` в репозитории бэкенда). Когда появится staging-API, достаточно
завести второй `site.env` с его адресом и своим `SITE_DEVICE_ID` — кода это
не касается.
