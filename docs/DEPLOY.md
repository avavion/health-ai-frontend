# Эксплуатация сайта

Выкатка, откат и то, что нужно завести на сервере один раз.

> **Адрес:** https://healthai.avavion.ru
> **Сервер:** тот же, что у API — VPS senko.digital (Германия), docker compose
> **Реестр образов:** ghcr.io/avavion/health-ai-frontend
> **Пайплайн:** [.github/workflows](../.github/workflows)

Схема повторяет выкатку API (`health-ai-backend/docs/DEPLOY.md`): те же цвета,
те же имена файлов, те же скрипты. Две разные схемы на одной машине означали
бы, что в три часа ночи придётся вспоминать, какая из них перед тобой.

---

## 1 · Как устроено

Blue/green: на сервере живут два поколения сайта, `web-blue` и `web-green`.
Трафик получает то, на которое указывает Caddy; второе стоит рядом
запущенным. Выкатка поднимает новое поколение в свободный цвет, ждёт от него
ответа и только потом переводит трафик.

**Фронт — Caddy, установленный на хосте, а не в compose.** Машина не пустая:
80 и 443 уже держит системный `caddy.service`, обслуживающий API, VPN и другие
сайты. Второй Caddy эти порты занять не смог бы, а отбирать их у работающего —
плохая мена. Поэтому цвета отдают себя на петлю, а хостовый Caddy проксирует
на живой.

```
        :443          /etc/caddy/health-web-upstream.conf
интернет ──► caddy.service ─────────┬──► web-blue    127.0.0.1:3110
             (на хосте,             │
              общий с API           └──► web-green   127.0.0.1:3111
              и другими сайтами)              │
                                              ▼
                                    health-api.avavion.ru
```

**Про порты.** 3000 и 3001 на этой машине заняты: 3000 держит панель
наблюдения (`GRAFANA_PORT` в `/opt/health-ai/.env`), 3001 — сосед. Поэтому
цвета сайта живут на 3110 и 3111. Внутри контейнера Next слушает свои 3000,
как ему и полагается, — это разные вещи, и конфликта здесь нет. Диапазон
задаётся в `.env` (`WEB_PORT_BLUE`, `WEB_PORT_GREEN`), и `deploy.sh` перед
подъёмом проверяет, что порт не занят кем-то посторонним.

Что это даёт:

- **Откат за секунду.** Прежнее поколение не остановлено, откат — это
  перезапись одной строки и `caddy reload`, без сборки.
- **Проверка до трафика.** Новый цвет обязан ответить `200` на `/api/health`
  **своей** версией и отдать лендинг: контейнер, который поднялся, но не
  собирает страницы, до пользователей не доходит.
- **Чужие сайты не страдают.** `caddy reload` перечитывает конфигурацию через
  админ-API на `127.0.0.1:2019`, root для этого не нужен, а неверную
  конфигурацию Caddy отвергает, оставляя работать прежнюю.

**Чего у сайта нет, в отличие от API.** Базы, миграций и дампа перед ними:
всё состояние живёт в API и в cookie у человека. Отсюда и правило двух
релизов сайта не касается — откатывать нечего, кроме кода. Сессии перезапуск
переживают: они в cookie и в базе API, а не в памяти сайта.

Файлы на сервере в `/opt/health-ai-web`:

| Файл | Откуда берётся | Что внутри |
|---|---|---|
| `docker-compose.yml`, `*.sh` | приезжают из репозитория при выкатке | конфигурация, версионируется вместе с кодом |
| `caddy-site.conf` | оттуда же, справочно | образец секции для хостового Caddy; заводится один раз руками |
| `.env` | создаётся руками один раз | домен и порты цветов |
| `site.env` | создаётся руками один раз | адрес API и идентификатор устройства сайта |
| `images.env` | пишет `deploy.sh` | какой образ в каком цвете |

## 2 · Первая настройка сервера

Один раз, под тем же пользователем, что выкатывает API.

### 2.1 Каталог

```bash
sudo mkdir -p /opt/health-ai-web && sudo chown "$USER" /opt/health-ai-web
```

Дальше запустите Deploy в GitHub Actions — он привезёт скрипты и шаблоны.
Первая выкатка упрётся в отсутствие `.env`, и это нормально: заполните файлы
и запустите её повторно.

### 2.2 Файлы окружения

```bash
cd /opt/health-ai-web
cp env.example      .env
cp site.env.example site.env
chmod 600 .env site.env
```

В `site.env` обязателен `SITE_DEVICE_ID` — постоянный UUID:

```bash
uuidgen | tr '[:upper:]' '[:lower:]'
```

У стенда и прода он должен быть разным: иначе они делят счётчик лимитов на
чтение правовых документов (§15.1).

### 2.3 Порты

Проверьте, что выбранные порты свободны, — 3000 и 3001 заняты:

```bash
sudo ss -ltnp 'sport = :3110'
sudo ss -ltnp 'sport = :3111'
```

Пусто — значит свободны. Если нет, поставьте другие в `.env` и поправьте
комментарий в секции Caddy (сам адрес туда пишет выкатка).

### 2.4 Файл адреса живого цвета

Его пишет выкатка, но завести и передать во владение надо под root:

```bash
sudo touch /etc/caddy/health-web-upstream.conf
sudo chown "$USER" /etc/caddy/health-web-upstream.conf
```

Это единственное, что скрипт пишет за пределами своего каталога.

### 2.5 Секция в хостовом Caddy

Содержимое `caddy-site.conf` добавляется в `/etc/caddy/Caddyfile` под root,
один раз:

```bash
sudo tee -a /etc/caddy/Caddyfile < /opt/health-ai-web/caddy-site.conf
sudo caddy validate --config /etc/caddy/Caddyfile
sudo systemctl reload caddy
```

Caddy отвергает неверную конфигурацию и оставляет работать прежнюю, поэтому
API и соседние сайты при ошибке не страдают.

> Секция ссылается на `health-web-upstream.conf`, который до первой выкатки
> пуст. `caddy validate` на пустой файл не ругается, но до выкатки домен
> ответит ошибкой — это ожидаемо.

### 2.6 Домен и CORS

- A-запись `healthai.avavion.ru` на тот же адрес, что и `health-api`.
  Сертификат Caddy выпустит сам при первом обращении.
- Домен сайта добавьте в `CORS_ORIGINS` в `/opt/health-ai/app.env` бэкенда
  (§16.3) и перевыкатите API. Сайт ходит в API своим сервером, и для основной
  работы CORS ему не нужен; список нужен там, где запрос делает сама страница.

### 2.7 Секреты репозитория

Те же, что у бэкенда, и на тот же сервер: `SSH_KEY`, `SSH_KNOWN_HOSTS`,
`SSH_HOST`, `SSH_USER`, при нестандартном порте — `SSH_PORT`. Переменные
(не секреты) `SITE_URL` и `SUPPORT_EMAIL` уезжают аргументами сборки образа:
Next подставляет `NEXT_PUBLIC_*` в код на сборке, а не читает при старте.

## 3 · Выкатка

Тег `v*` в `main` — и дальше само:

```bash
git tag v1.0.0 && git push origin v1.0.0
```

Окружение `production` в настройках репозитория держит ручное подтверждение:
тег ставят и по ошибке, а выкатка по нему уезжала бы молча.

Вручную с сервера:

```bash
/opt/health-ai-web/deploy.sh \
  --image ghcr.io/avavion/health-ai-frontend:sha-abc1234 \
  --version v1.0.0
```

Что делает скрипт по шагам:

1. Определяет живой цвет по `health-web-upstream.conf` и берёт свободный.
2. Проверяет, что порт свободного цвета не занят посторонним.
3. Тянет образ и поднимает контейнер.
4. Ждёт `200` на `http://127.0.0.1:<порт>/api/health` **со своей версией** —
   кода ответа мало: на порту мог остаться прежний контейнер этого цвета.
5. Проверяет, что цвет отдаёт лендинг `/ru`, а не только отвечает здоровьем.
6. Переписывает адрес и делает `caddy reload`.
7. Проверяет через публичный адрес, что снаружи отвечает новая версия;
   не дождался — возвращает трафик обратно.

Не поднявшийся цвет останавливается и удаляется, `images.env` возвращается к
прежнему виду, трафик остаётся там, где был.

## 4 · Откат

```bash
/opt/health-ai-web/rollback.sh
```

Возвращает трафик на предыдущий цвет — он всё это время оставался запущенным.
Около секунды, без сборки.

Если предыдущий цвет уже не запущен (например, после двух выкаток подряд),
скрипт скажет об этом и предложит выкатить нужную версию заново:

```bash
cat /opt/health-ai-web/images.env      # что в каком цвете
/opt/health-ai-web/deploy.sh --image ghcr.io/avavion/health-ai-frontend:sha-<прежний> --version <прежняя>
```

Теги образов — короткие sha коммитов, они неизменны: по тегу всегда видно,
какой именно код поднят.

## 5 · Когда что-то не так

Порядок разбора — от дешёвого к дорогому:

```bash
cd /opt/health-ai-web
cat images.env                                    # что выкачено
cat /etc/caddy/health-web-upstream.conf           # куда идёт трафик
docker ps --filter name=health-ai-web             # какие цвета подняты
docker logs --tail 100 health-ai-web-blue         # что говорит сайт
curl -sS http://127.0.0.1:3110/api/health         # отвечает ли цвет
curl -sS https://health-api.avavion.ru/health     # жив ли API
sudo journalctl -u caddy -n 50                    # дошёл ли запрос до сайта
```

| Симптом | Причина | Что делать |
|---|---|---|
| Экраны дневника отдают ошибку, лендинг работает | API недоступен или сменил адрес | проверить `API_BASE_URL` в `site.env` и здоровье API |
| Правовые страницы показывают «документ временно недоступен» | API отвечает 4xx на `/legal/*` | проверить `SITE_DEVICE_ID` и лимит §15.1 |
| Всех разлогинило | отозвана цепочка сессий на API | смотреть лог API: повторное предъявление refresh-токена (§4.2) |
| 502 от Caddy | живой цвет не запущен | `docker ps`, затем `rollback.sh` |
| Выкатка встала на «порт занят не нашим контейнером» | кто-то занял 3110/3111 | `sudo ss -ltnp 'sport = :3110'`, освободить или сменить порты в `.env` |
| Выкатка встала на публичной проверке | Caddy ещё выпускает сертификат либо секция не заведена | `sudo caddy validate --config /etc/caddy/Caddyfile`, `journalctl -u caddy` |

## 6 · Стенд

Отдельного стенда у сайта нет: он поднимается локально против API разработки
(`make up` в репозитории бэкенда). Когда появится staging-API, достаточно
завести второй `site.env` с его адресом и своим `SITE_DEVICE_ID` — кода это
не касается.
